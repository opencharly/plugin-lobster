## Summary

This PR lands the **LOBSTER workflow engine** module into `plugin-lobster` — the repo skeleton (`README.md`,
`AGENTS.md`, `LICENSE`, root `charly.yml`, `.github/workflows/`) was the `repo-setup` leg; the Go module is
this one. The plugin is the one thing in the wave that **executes** a workflow: `kind:pipeline` (lobster
syntax carrying charly's own step grammar) is resolved and validated by `plugin-pipeline`, lowered by
`sdk/workflowkit.Lower` into a `(workflow.lobster, charly.yml)` pair, and dispatched here as
`InvokeProvider("workflow", "lobster", workflow-<op>)`. This plugin decodes that request, runs the pair, and
answers in lobster's **tool-mode envelope v1**, so its output is interchangeable with upstream lobster's.

| capability | ops / verbs |
|---|---|
| `workflow:lobster` | `workflow-run` (execute) · `workflow-resume` (answer an approval/input gate by token or short id) · `workflow-schedule` (apply/list/remove/run-now the systemd-**user** timers) · `workflow-emit` (lower the IR to a consumer's on-disk form) |
| `command:lobster` | `charly lobster import <file>` (upstream `.lobster` → `kind:pipeline`) · `export <name>` (write the pair **upstream lobster can run** — charly steps are plain `charly task` invocations) · `doctor` |

**Nothing charly-specific is special-cased.** Every charly-shaped step runs by invoking `charly` itself

**`cost_test.go` — the `cost_limit` ceiling (`cost.go`).** This engine spends nothing of its own: the
`pipeline:` stdlib refuses the LLM stages, so the ceiling is a **read** of the `_meta.cost` block a step
reports plus the workflow's own cap — and that read and cap are the whole of the file's behaviour, so they
are what is pinned: everything recorded off `_meta.cost` (model, both token counts, dollars, the per-step
ledger and the run total, in step order); the negative control — a step that reported nothing, non-object
JSON, or a `_meta` without a `cost` contributes **no entry and no dollars**, so the ledger is a record and
not an estimate; each `action` at the boundary (`stop` fails naming **both** figures, `warn` prints and
continues, an empty action defaults to `warn`, and a total exactly **at** the cap is not over it); and the
tracker's one piece of state — `warn` is latched to a single line however many steps push the total higher,

**`cli_doctor_test.go` — `doctor` (`cli.go`).** `doctor` is an operator's first look at why a step will not
run, so its contract is: report the resolved surface and **always exit 0**. The tests drive it through the

persists) — and pin both branches of each: an unresolvable `CHARLY_BIN` **warns AND still exits 0** (a
diagnostic that exits non-zero on a diagnosis is a trap in a script), an existing state dir reads `present`
while a missing one reads `not created yet`, and the `pipeline stages:` line equals `newRegistry().names()`
exactly — that is the line telling an operator whether the `pipeline:` step in their workflow is supported,
so it must be the registry itself and not a hand-kept list. It deliberately does **not** assert the systemd line: that comes from a real `systemctl --user` query, a
property of the host, so pinning one outcome would pin the test host — the query is real, its result is
simply not the contract. Both files are in-process and cross no live boundary.
