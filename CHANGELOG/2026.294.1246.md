# 2026.294.1246 — test(bed): grade the lane pool — `check-lobster-local` carries the `lanes:` witness

## Summary

`check-lobster-local` is this repo's engine-semantics witness, and the lane pool was the one arm it
could not grade: a `lanes:` step could not pass on merged refs, because the FRONT-END that
validates a pipeline pinned `sdk v0.2026293.2302`, whose workflowkit `execArms` has no `lanes`, so
`ValidatePipeline` refused the step before any engine saw it. `opencharly/plugin-pipeline#49`
carried the arg-map widening plus `sdk v2026.294.1003` / `spec v2026.294.929` and merged as the tag
`v2026.294.1135`. This PR spends that unblock: it lands the step `opencharly/plugin-lobster#7`
handed over, on the merged front-end, so the committed bed grades the pool by default instead of in
a throwaway clone.

The chain is complete: the arm (`#10`, tag `v2026.294.1100`), the front-end (`#49`, tag
`v2026.294.1135`), and now this witness (`#7`).

**One file, `charly.yml`, 119 insertions and 13 deletions.** Three things in one commit:

1. **The step, verbatim from `#7`.** Its 93 lines are the diff's added-lines 26..118 with no edit;
   both sides were extracted and `diff` was asked, not a human (below). It sits after
   `lobster-for-each` and before `lobster-composition`, as the handover notes say. It asserts four
   properties, each able to fail on its own:
   - the ordered loop result `["0:a","1:b","2:c","3:d"]` — every item visited exactly once, each
     lane reading **its own** `$it.json.k` + `$ix.json`, in **item order** (`batch.go:367-378`
     installs item/index as a per-item SCOPE; `batch.go:238-241` makes the loop's value its array of
     iteration results, not completion order);
   - an in-flight counter peaking at exactly `batch_size` = 2 — more than one lane ran, and a third
     never did (`batch.go:275-330`: one channel feeding exactly `batch_size` workers, a pool and not
     a spawn per item);
   - a failing lane turning the run into `status=error`, so the step after the loop never runs
     (`batch.go:346-352`; `engine.go:519` returns the loop's error);
   - a `lanes:` step without `batch_size` being refused.
2. **The gate's message text, deliberately.** The step asserts `step "<id>": lanes requires
   batch_size >= 1 (the pool width)` (`sdk/workflowkit/validate.go:238`), NOT the engine's
   `Workflow step <id> lanes requires batch_size >= 1 (the pool width)` (`lobster.go:496`,
   `batch.go:220`). The bed drives the AUTHORED path, where `ValidatePipeline` fires before any
   engine sees the step, so the engine's wording is unreachable from a bed and asserting it would be
   an assertion that never runs. That decision and its why are the step's own comment, kept exactly
   as `#7` recorded it.
3. **The header and the bed `description:`.** The header states its own invariant — "the step counts
   and their result" must stay true under the file's own edits — so a landed step moves it. The
   coverage list and the description now name the lane pool, the measured state is `13 steps: 13
   passed, 0 failed, 0 skipped` / `errors: 0` / `warnings: 0` / `ok: true`, and the paragraph that
   said the arm "cannot grade" is replaced by one that says it does, naming the front-end pin that
   blocked it and the tag that cleared it. Leaving `12/12` there would have been exactly the
   contradiction `#10`'s round 1 was blocked on — in the same file.
