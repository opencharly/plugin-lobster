## Summary

`parallel:` fans out over branches that are STATIC in the file. `for_each:` walks a runtime
collection but does so IN ORDER — upstream lobster's own semantics, where `batch_size` only decides
when `pause_ms` fires. Neither can express a **concurrent pool over a collection that only exists at
run time**:

```yaml
- id: fan
  lanes: $seed.json        # the RUNTIME collection (a step ref or a JSON array template)
  batch_size: 4            # the POOL WIDTH
  item_var: pr             # per-lane refs: $pr.json / $ix.json
  index_var: ix
  steps: [...]             # the body, run once per item
```

It shares ONE loop driver with `for_each` (`runLoop` / `runLoopItem`), so the two arms cannot drift;
`for_each` keeps upstream's sequential semantics untouched. The four properties from the operator
ruling (`plugin-pipeline#43`), each with the test that fails without it:

| property | mechanism | test |
|---|---|---|
| a stopped engine does not orphan children | a `signal.NotifyContext`-style bridge at the op boundary; the shell arm already SIGKILLs the child's process group on context end | `TestLanesStopSignalKillsInFlightChildren` |
| per-lane binding is a SCOPE, never process env | `item`/`index` are synthetic step RESULTS in a per-lane COPY of the result set (`results.scoped`); nothing touches process env | `TestLanesBindPerItemWithoutProcessEnv` |
| ANY failed lane fails the step | per-index failures recorded, the pool cancelled, the LOWEST OBSERVED failure index reported | `TestLanesAnyFailedLaneFailsTheStep` |
| the width is a POOL, not a spawn per item | exactly `batch_size` workers pull indices from one channel | `TestLanesPoolWidthBoundsConcurrency` (width 1 and 3) |

the loop's ordered result array is `["0:a","1:b","2:c","3:d"]` (every item visited exactly once,

the next step never runs; and a `lanes:` step with no `batch_size` is refused. Its negative control:
binding a constant instead of the item in `runLoopItem` makes the same step FAIL and report
`["0:","1:","2:","3:"]`.

the AUTHORED path, where the gate fires first, so the engine's wording is unreachable from a bed —
the bed asserts the GATE text, and says so in the step's own comment. This PR asserts neither: the
bed step is deliberately NOT in this diff, because a step that cannot pass on merged refs would put
an assertion in `main` that can never hold.
